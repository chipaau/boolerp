# API conventions

Status: agreed 2026-09-30 (H1, C64–C70). Every business endpoint follows these
conventions. Errors follow the [HTTP foundation](http.md) (RFC 9457 problem details,
C37); request input handling is H2.

## Versioning (C64)

Business endpoints live under `/api/v1/`. A breaking change gets a new version prefix
(`/api/v2/`), which can run alongside the old one. Operational endpoints stay
unversioned: `GET /api/healthz` (liveness) and `GET /api/readyz` (readiness).

Why: self-hosted installs run different releases (C09), so clients and servers will not
always match; a version in the path is visible in logs, traces (`http.route`), and docs,
and chi routes it with a `Route("/api/v1", ...)` group.

## JSON field names (C65)

Request and response bodies use camelCase: `{"firstName": "Aisha", "hiredAt": "2026-01-15"}`.

This matches the React/TypeScript frontend without a conversion layer. It does not apply
to RFC 9457's own fields (`type`, `title`, `status`, `detail`, `instance`), log attributes
(`request_id`), OpenTelemetry attributes (`http.route`), or database columns, which stay
snake_case and map to JSON through Go struct tags.

## Paths and actions (C66)

- Plural nouns: `/api/v1/employees`, `/api/v1/employees/{id}`.
- kebab-case for multi-word names: `/api/v1/leave-requests`.
- At most one level of nesting, only for real ownership: `/api/v1/employees/{id}/documents`.
- The tenant never appears in the path; it comes from the request's host and identity.
- Business actions that are not plain create/read/update/delete use
  `POST /api/v1/{resources}/{id}/{action}`, for example
  `POST /api/v1/employees/{id}/terminate`. Each action is its own endpoint, with its own
  permission (Cerbos, C21) and audit record, instead of a status field hidden in a
  generic `PATCH`.

| Operation | Method and path |
| --- | --- |
| List | `GET /api/v1/employees` |
| Create | `POST /api/v1/employees` |
| Read | `GET /api/v1/employees/{id}` |
| Update (partial) | `PATCH /api/v1/employees/{id}` |
| Delete | `DELETE /api/v1/employees/{id}` |
| Business action | `POST /api/v1/employees/{id}/terminate` |

## Identifiers (C67)

Resource IDs are UUIDv7, generated by PostgreSQL 18's native `uuidv7()` and stored as
the `uuid` type. In JSON they are strings:
`"id": "01a0eec6-7f40-7f0f-945b-d5b1731b756c"`.

UUIDv7 does not reveal counts or invite guessing neighbouring IDs (as `/employees/42`
would), and its time order keeps primary-key indexes efficient. It is the same format as
request IDs (C34).

## Lists: pagination (C68)

The standard list format uses page and size, with a total:

```text
GET /api/v1/employees?page=3&pageSize=50
```

```json
{"items": [ ... ], "page": 3, "pageSize": 50, "total": 1234}
```

- `page` starts at 1; `pageSize` has a per-endpoint default and a maximum (normally 100).
- Values outside the allowed range are a 400 problem response.

Lists that grow without bound (for example the audit log, step 9, or event feeds) may
instead use cursor pagination as a documented exception:
`?limit=50&cursor=...` returning `{"items": [ ... ], "nextCursor": "..."}`.

## Lists: filtering and sorting (C69)

- Filters are named query parameters: `?status=active&departmentId=...`.
- Ranges use explicit pairs: `?hiredFrom=2025-01-01&hiredTo=2025-12-31`.
- Free-text search, where supported, uses `q`: `?q=aisha`.
- Sorting uses `sort`, comma-separated, with `-` for descending: `?sort=-hiredAt,lastName`.
- Every filter and sort field is declared per endpoint (allow-listed). Unknown
  parameters or sort fields are a 400 problem response, never silently ignored, so
  nothing reaches SQL that was not declared.

## Request input and validation errors (C71–C74)

Request bodies are Go structs with `json` and `validate` tags, decoded by
`httpinput.Decode`, which writes the error response itself:

```go
type CreateEmployeeRequest struct { // illustration only; the employee model is D11
	FirstName string `json:"firstName" validate:"required,max=100"`
	Email     string `json:"email"     validate:"required,email"`
}

func (h *Handler) create(w http.ResponseWriter, r *http.Request) {
	var req CreateEmployeeRequest
	if !httpinput.Decode(w, r, &req) {
		return // 400, 413, 415, or 422 already written
	}
	// req is valid ...
}
```

| Failure | Status | `type` |
| --- | --- | --- |
| Body empty, malformed, or more than one JSON value | 400 | `about:blank` |
| Body over `APP_HTTP_MAX_BODY_BYTES` | 413 | `about:blank` |
| `Content-Type` not `application/json` | 415 | `about:blank` |
| Wrong JSON type, unknown field, failed rule, invalid query parameter | 422 | `https://bool.mv/problems/validation-error` |

A validation problem lists every failing field (RFC 9457's `errors` pattern), never the
submitted values:

```json
{"type": "https://bool.mv/problems/validation-error", "title": "Unprocessable Content",
 "status": 422, "detail": "The request has 2 invalid fields.", "instance": "urn:uuid:...",
 "errors": [
   {"pointer": "#/email", "code": "email", "detail": "must be a valid email address"},
   {"parameter": "pageSize", "code": "max", "detail": "must be at most 100"}]}
```

- `pointer` is a JSON Pointer to a body field using JSON names (`#/items/0/name`);
  `parameter` names a query parameter; `code` is the rule (`required`, `email`, `max`,
  `oneof`, `type`, `unknown`, `format`, ...).
- Go's `encoding/json` stops at the first wrong-type or unknown field, so those are
  reported alone; unknown fields and invalid dates have no path and point at the whole
  body (`#`), naming the unknown field in `detail`.
- Rules that need data (unique email, existing department) are checked by the
  application layer and database constraints, which return `problem.ValidationError`;
  the response has the same format.

## Contract and frontend types (C74)

No OpenAPI contract is maintained yet (C70 was replaced): the Go request and response
structs are the source of truth. When the frontend's API contract is standardised (C128), frontend TypeScript
types and Zod schemas are generated from them; options include `hypersequent/zen` (Zod
directly from validator tags) and OpenAPI with `orval` (typed client and TanStack Query
hooks). The frontend's validation is for user feedback only; the API always validates.
