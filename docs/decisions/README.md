# Decision register

Updated: 2026-10-08. Decisions are made one at a time.

## Confirmed baseline

| ID | Decision or requirement |
| --- | --- |
| C01 | Build the Go API in the existing monorepo; previous implementation choices are not binding. |
| C02 | Use a modular monolith with hexagonal domain/application/adapter boundaries. |
| C03 | PostgreSQL is the application database. Multi-database portability is not a goal. |
| C04 | Redis is retained for caching; caching is a required backbone capability. |
| C05 | Audit and tracing are required, distinct backbone capabilities. |
| C06 | Current business scope is HRMS employee records only, supported by the platform backbone. |
| C07 | Frontend integration is deferred. **Superseded by C128.** |
| C08 | Development Compose started with `api`, `app`, `postgres`, and `redis`. This was the starting set, not a limit (clarified 2026-09-30): services are added deliberately when a step needs them, such as `jaeger` (C63). |
| C09 | Support hosted multi-tenancy, default domains, verified custom domains, and self-hosting with the same codebase/release. |
| C10 | English UI; Dhivehi content only where needed. |
| C11 | Distribute binaries/containers with licensing controls that discourage unauthorized resale; binaries are not tamper-proof. |
| C12 | Project documentation lives in docs/; substantive agent rules live in .claude/. AGENTS.md links to CLAUDE.md. |
| C13 | Make the remaining decisions sequentially and confirm schemas table by table before implementation. |
| C14 | Scaffold the proposed structure and start with a simple API entry point; build subsequent layers incrementally. |
| C15 | The canonical repository is the GitHub erp checkout; branch from updated develop and preserve the newer frontend and security-review work. |
| C16 | Implement platform delivery step 1: runtime configuration, validation, structured logging, redaction, and explicit runtime wiring. |
| C17 | After merging step 1 into the updated dev branch, implement step 2 (HTTP foundation) on a new branch. |
| C18 | After step 2 merges, implement step 3 on a new branch using pgx/v5 pgxpool and Goose; defer sqlc until the first table is approved. |
| C19 | Use chi as the Go API HTTP framework. Step 2a moved the HTTP foundation from `net/http` ServeMux to chi/v5; shared HTTP middleware behavior is preserved. Canonical redirect behavior is recorded in C23. |
| C20 | Use Ory Kratos as the identity and authentication system; session, provisioning, domain, and account contracts remain open. |
| C21 | Use Cerbos as the authorization policy engine; roles, resources, policy inputs, and revocation behavior remain open. |
| C22 | Use the S3 API for file/object storage; use `chipaau/minio`, the project's exact MinIO fork, as the development server. Production provider and Go SDK remain open. |
| C23 | Redirect paths changed by `path.Clean` with 307 Temporary Redirect, preserving the request method, body, and query. This intentionally differs from ServeMux's canonical-path redirect behavior. **Superseded by C39.** |
| C24 | Build the API in order: a simple chi server, then configuration, then logging, then the remaining platform steps (the roadmap). Tool selections and contracts from C14–C23 stand. |
| C25 | Liveness uses chi's `middleware.Heartbeat("/api/healthz")`: `GET`/`HEAD` return `200` with `text/plain` body `.`. This replaces the earlier JSON `{"status":"ok"}` liveness response, following the framework-first rule. **Superseded by C36.** |
| C26 | Load runtime configuration from the process environment with `github.com/caarlos0/env/v11` (v11.4.1). The binary does not read dotenv files; `joho/godotenv` was considered and rejected because Compose already supplies `.env` values and reading files from the working directory is a risk for self-hosted installs. |
| C27 | Validate configuration with `github.com/go-playground/validator/v10` struct tags, chosen over a hand-written `Validate()` so one validation approach can later serve request input as well. Request-validation use remains to be confirmed when HTTP input is added. Confirmed for request bodies by C74. |
| C28 | Use `github.com/stretchr/testify` (v1.12.1) for test assertions, limited to the `require` and `assert` packages; `mock` and `suite` are not adopted. Tests otherwise use the standard `testing` package. |
| C29 | Redact sensitive log attributes with slog's built-in `HandlerOptions.ReplaceAttr` hook and the name-based word list in [observability](../platform/observability.md); the list includes `passwd`, `bearer`, `jwt`, `session`, and `encryptionkey` so session identifiers are never logged. `m-mizutani/masq` was considered and not adopted (pre-1.0, single maintainer; deep struct inspection is not required because call sites must log deliberate safe fields). HTTP request logging in step 2 uses `go-chi/httplog` with this logger rather than a custom request logger. |
| C30 | `APP_SHUTDOWN_TIMEOUT` must be at least `APP_HTTP_WRITE_TIMEOUT` (validator `gtefield`), so graceful shutdown can finish any request the server allows. Defaults: shutdown `35s` (maximum `10m`), Compose `stop_grace_period: 40s`. Trade-off: a deploy can wait up to 35s while a slow request finishes. |
| C31 | `net/http` server diagnostics (`http.Server.ErrorLog`) are logged at WARN, not ERROR, because most are client-caused (TLS handshake failures, malformed requests). Application failures and recovered panics (step 2e) log at ERROR. |
| C32 | CI runs `go test -race`. The Go dev and CI image (`docker/go.Dockerfile`) is the Debian-based `golang:1.27` because the race detector needs cgo; the production build image (`docker/api.Dockerfile`) is unchanged. |
| C33 | The server always generates its own request ID and returns it in `X-Request-Id`; any client-supplied `X-Request-Id` is discarded, because request IDs are log evidence. Accepting IDs from a trusted proxy is left to step 2f. |
| C34 | Request IDs use `github.com/go-chi/traceid` (v0.3.0; UUIDv7, response header, `request_id` on every context-aware log record) instead of chi's `middleware.RequestID`, whose IDs embed the server hostname and would expose container/pod names to clients. Request logging uses `github.com/go-chi/httplog/v3` with the OpenTelemetry schema, in line with the planned OpenTelemetry tracing. |
| C35 | Every response written by the API is JSON: handler results, errors (404, 405, 413, 500), and liveness. Exceptions are responses produced by Go's HTTP server before any application code runs (for example 400 for a malformed request, 431 for oversized headers, 505), which it writes as plain text with no hook to change them, and connections closed by a timeout, which receive no response. |
| C36 | Liveness is a normal chi route, `GET /api/healthz` returning `200` `{"status":"ok"}` (`HEAD` via `chi/middleware.GetHead`), replacing `middleware.Heartbeat` (C25) to satisfy C35. It receives a request ID but is excluded from request logs with httplog's `Skip` option. It checks no dependencies. |
| C37 | Error responses follow RFC 9457 problem details (`application/problem+json`), written by `internal/platform/problem` on the standard library: no maintained Go library adds more than the five-member struct (documented gap). `type` is `about:blank` with the HTTP status phrase as `title` until specific problem types are defined; `instance` is `urn:uuid:<request ID>`, matching `X-Request-Id` and the `request_id` log attribute; `detail` must be safe for clients. chi's `NotFound`/`MethodNotAllowed` hooks return problem details; the 405 handler rebuilds `Allow` with chi's route lookup because chi does not pass allowed methods to custom handlers (documented gap). Every response also carries `X-Content-Type-Options: nosniff` (chi `SetHeader`). |
| C38 | Handler panics are handled by `problem.Recoverer`, registered directly inside the request logger: it logs one ERROR record (`panic recovered`, with request ID and stack) and answers 500 problem details; if the response has already started it aborts the connection with `http.ErrAbortHandler` instead of appending to a partial body; deliberate `http.ErrAbortHandler` panics pass through unlogged. Panic values are not logged, except Go runtime errors (runtime-generated messages); other values are logged by type. chi's `Recoverer` and httplog's `RecoverPanics` cannot write a response body and log outside the redacted logger (documented gap); httplog's `RecoverPanics` stays enabled only as a backstop. |
| C39 | Paths match exactly: no path cleaning and no canonical redirects. Non-canonical paths (`/api//x`, `/api/x/`) are 404 problem details. API clients call exact URLs, and silent rewriting (chi `CleanPath`) risks proxy/application path-interpretation mismatches. Supersedes C23. Traefik cleans paths itself before forwarding, so the API only receives the cleaned form. |
| C40 | The client IP is taken from `X-Forwarded-For` by counting trusted proxy hops (`APP_HTTP_TRUSTED_PROXY_HOPS`, chi `ClientIPFromXFFTrustedProxies`): with N hops the client is the Nth entry from the right, and entries further left are client-supplied and ignored. `0` (default) ignores forwarded headers and uses the connection address (chi `ClientIPFromRemoteAddr`); Compose uses `1` for Traefik. Chosen over trusted CIDR ranges because container proxy IPs are dynamic and, on Docker Desktop, the client address falls inside the proxy's subnet. Deployments must set the real hop count, verify it once with a request from a known IP, and make the API reachable only through the proxy. |
| C41 | Cross-origin access is allowed only for configured origins (`APP_HTTP_ALLOWED_ORIGINS`, exact `scheme://host[:port]`, no wildcards; empty by default). `go-chi/cors` (v1.2.2) lets those origins read responses and answers preflight requests; it is installed only when the list is non-empty, because it treats an empty list as "allow all". Go's `http.CrossOriginProtection` rejects cross-origin state-changing browser requests (POST, PUT, PATCH, DELETE) from other origins with 403 problem details; same-origin and non-browser requests pass. Credentialed CORS is off until the session contract (D04); per-tenant custom-domain origins will need `AllowOriginFunc` and `AddTrustedOrigin` from the domain registry. |
| C42 | The pgxpool is created lazily at startup (no connection until first use), so the API starts and liveness answers while PostgreSQL is down; readiness reports database reachability. Invalid connection settings fail startup with a fixed message; pgx's parse error, which contains the connection string, is never wrapped. `APP_DB_MAX_CONNS` (default 20, 1–1000) is the only pool setting in configuration; others keep pgx defaults. |
| C43 | The API's PostgreSQL connection is configured with separate settings instead of one DSN: `APP_DB_HOST`, `APP_DB_NAME`, `APP_DB_USER`, `APP_DB_PASSWORD` (file-only as `APP_DB_PASSWORD_FILE` since C80; required, no defaults, so no credentials in code), `APP_DB_PORT` (5432), and `APP_DB_SSLMODE`. The password stays a single secret value suitable for secret managers, needs no URL escaping (the connection URL is built with `net/url`), and errors name the exact setting. `APP_DB_SSLMODE` defaults to `verify-full` and accepts `disable`, `require`, `verify-ca`, `verify-full`; pgx's `allow` and `prefer` are rejected because they silently fall back to unencrypted connections. Compose sets `disable` and derives name, user, and password from the PostgreSQL role settings. Chosen over libpq `PG*` variables, which pgx reads directly from the process environment and would bypass configuration validation. |
| C44 | Configuration is grouped by concern, one file and struct per group in `internal/platform/config`, like Laravel's config files: `app.go` (`App`: `APP_ENV`, `APP_PORT`, `APP_SHUTDOWN_TIMEOUT`), `log.go` (`APP_LOG_*`), `http.go` (`APP_HTTP_*`), `database.go` (`APP_DB_*`). Groups use `caarlos0/env` `envPrefix`, so variable names are unchanged. Go field names were kept unique across groups because `caarlos0/env` parse errors report only the field name; C53 removed that rule by parsing each group separately. Rules spanning groups (C30) use validator struct-level validation, since validator's cross-struct tags cannot reach sibling structs. Environment variables remain the only source (C26). |
| C45 | `GET /api/readyz` reports whether the API's dependencies (currently PostgreSQL, via `pool.Ping`) can be reached within `APP_DB_PING_TIMEOUT` (default 2s, max 1m): `200` `{"status":"ready"}` or `503` problem details with a generic detail. The cause is logged at WARN with the request ID, never returned; successful checks are not request-logged. The Compose health check (and so Traefik routing) stays on liveness (`/api/healthz`): with a single instance, routing away during an outage only replaces the API's JSON 503 with Traefik's plain-text error, and restarting the process does not fix a dependency. Readiness is for multi-instance load balancers and orchestrators (for example a Kubernetes `readinessProbe`) and monitoring. |
| C46 | Migrations run through Goose as a library in `cmd/migrate`, with SQL files embedded in the release binary (`internal/platform/postgres/migrations/sql`), a PostgreSQL advisory lock (`lock.NewPostgresSessionLocker`) serializing concurrent runs, history in `migrations.goose_db_version`, and logs through the application logger. Migrations are forward-only: only `-- +goose Up` sections, no down command; mistakes are fixed forward and recovery uses backup/restore (D10). Chosen over the goose CLI so each release carries its own migrations with no extra tool. The command pings first so bad credentials fail even with nothing to apply, and reports failures without statement text or PostgreSQL detail. |
| C47 | `cmd/migrate` uses its own `MIGRATE_DB_*` settings (host, port, name, user, password, sslmode; same rules as C43) and reads nothing from `APP_*`; the API never receives them. The migration role can change the schema and the runtime role cannot, so a compromised API cannot alter or drop schema objects, and migrations can connect to a different endpoint than the API (directly, bypassing a transaction pooler such as PgBouncer). |
| C48 | Direction for when the first module table is approved: each module owns its migrations in its own folder (`internal/modules/<module>/migrations`, corrected by C95), embedded by that module's package, with its own Goose history table (`migrations.<module>_version`). `cmd/migrate` runs the modules in a fixed dependency order (tenancy, identity, authorization, audit, hrms), so tables referenced by another module exist first. Each module's run keeps C46's lock, forward-only rule, and safe errors. Chosen over one global folder (modules would not own their migrations) and over merging folders into one sequence (cross-module version collisions and custom merging code). Implemented with the first table (`users`, C94, C95); the empty global folder was removed. The order is the edition's list of modules (C95). **Paths revised by C95, C122, and C125.** |
| C49 | Local development data is disposable: Compose volumes (such as `erp_pgdata`) may be reset whenever needed. With an empty `pgdata` volume, PostgreSQL creates the `erp` database and `10-roles.sh` creates the runtime and migration roles and the `migrations` schema on first start, as Laravel Sail does; tables come from `cmd/migrate`. The old API's development data was removed on 2026-09-29. |
| C50 | Development and test data comes from seeds, like Laravel seeders: a Go command (`cmd/seed`) that creates data through the application's use cases, so seeded data passes the same tenant, validation, and audit rules as real data, and seeded users can log in through Kratos (C20). SQL seed files (Goose's `WithDisableVersioning`) were not chosen because they bypass those rules and cannot create Kratos identities. Seeds run in every environment except production, and fail closed: `cmd/seed` requires `APP_ENV` to be set explicitly (the API's `dev` default does not apply) to `dev`, `test`, or `staging`, refuses otherwise, and is not built into the production image. Seed data is generated, never real personal data, and can run repeatedly without duplicating. **Implemented** (2026-10-02): `cmd/seed`, the `seed` Compose service, and the identity module's `EnsureAccount`. **Exception** at the user's request: the team's own work emails (`ibrahim@`, `shifau@`, `mariyam@bool.mv`) are seeded as development accounts with first names and placeholder phones, the password `password` set in the seeder (a public development value, not a secret, so not a C80 file), and a Google stand-in sign-in; because that password is public, they are seeded **only in `dev`**. See [development](../development.md#seed-data-c50-c118). |
| C51 | The Redis client is `github.com/redis/go-redis/v9` (v9.22.0, BSD-2): the official and most widely used Go client, one method per command, and an official OpenTelemetry add-on (`redisotel`) for step 5. Chosen over `valkey-io/valkey-go`/`rueidis`, whose built-in client-side caching has no measured need here. Both clients work with Redis and Valkey servers, so this does not choose the server; the server's license (Redis 8: AGPLv3/RSALv2/SSPLv1; Valkey: BSD) is a D08/D10 question. |
| C52 | Redis is optional at runtime: it is a cache and PostgreSQL holds the data. When Redis is unavailable the API stays ready (`/api/readyz` does not check Redis), cache operations fail fast, and callers fall back to PostgreSQL; the outage is logged at WARN. This applies to caching only: any later use where a fallback is unsafe (rate limits, security data, a job queue under D09) needs its own failure rule. |
| C53 | Redis is configured with separate settings, like C43: `APP_REDIS_HOST` (required), `APP_REDIS_PORT` (6379), `APP_REDIS_USERNAME` and `APP_REDIS_PASSWORD` (`APP_REDIS_PASSWORD_FILE` since C80; optional; production should set them), `APP_REDIS_DB` (0–15), `APP_REDIS_TLS` (default on, certificate verified; Compose off), and `APP_REDIS_TIMEOUT` (500ms) bounding connect, read, and write. In code: no command retries, one connection attempt, request deadlines respected, lazy connection, pool size at go-redis's default. With go-redis's defaults a single call to an unreachable Redis took 1m42s in testing; with these settings it fails in about 0.2s. go-redis's own diagnostics are routed to the application logger at WARN (`redis.SetLogger`). Config groups are now parsed separately, so groups may reuse field names (`DB.Port`, `Redis.Port`); this replaces C44's unique-field-name rule. |
| C54 | Tracing is built on OpenTelemetry (Go API/SDK v1.46.0): the vendor-neutral standard, exporting over OTLP to Tempo, Jaeger, Elastic, Datadog, and others, with official instrumentation for `net/http` and go-redis and the maintained `exaring/otelpgx` for pgx. Chosen over vendor SDKs (lock-in, and every self-hosted install would need that vendor) and log-only IDs (no timing or downstream visibility; does not satisfy C05). Tracing is built now (step 5) rather than deferred, so later steps are instrumented from their first line. |
| C55 | Tracing is configured with the standard OpenTelemetry environment variables (`OTEL_TRACES_EXPORTER`, `OTEL_EXPORTER_OTLP_ENDPOINT`/`_HEADERS`/`_PROTOCOL`, `OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`, `OTEL_TRACES_SAMPLER`, ...), read by the SDK and `go.opentelemetry.io/contrib/exporters/autoexport` (v0.71.0), not by `config.Load`: settings defined by an external cross-language standard keep that standard's names, a deliberate exception to `APP_*` (C26). Export is **off unless `OTEL_TRACES_EXPORTER` is set** (autoexport's own default, OTLP to localhost, is overridden); when off the SDK is not started and a no-op provider is used, so tracing costs nothing. Unknown values fail startup. `autoexport` was kept over a hand-written HTTP-only switch despite +3 MB binary and +21 indirect modules (gRPC, Prometheus, metric/log exporters), because it implements the specification's full exporter selection including OTLP over gRPC, which many collectors use. Propagation is W3C Trace Context only (no Baggage, which carries arbitrary client data). OpenTelemetry's errors go to the application logger at WARN. The provider is passed explicitly to instrumentation instead of set globally. |
| C56 | Sampling keeps the SDK default, `parentbased_always_on`: every request is traced unless a trusted parent context says otherwise. Deployments change it with `OTEL_TRACES_SAMPLER`/`OTEL_TRACES_SAMPLER_ARG` (for example `parentbased_traceidratio` at `0.1`) without a release. Whether incoming parent context is trusted at all is step 5b's decision. |
| C57 | HTTP server spans come from the official `otelhttp` (v0.71.0) wrapping the whole router, so a request's span covers all middleware. Spans are named by chi's route pattern (`GET /api/employees/{id}`) with the `http.route` attribute; unmatched requests keep the method alone, so raw paths never become span names. A small chi middleware (`spanNameFromRoute`) renames the span after routing: the documented gap is that otelhttp renames from `r.Pattern`, but chi sets `Pattern` on its own copy of the request, which otelhttp never sees. Chosen over `riandyrn/otelchi` (third-party, pre-1.0, its own copy of the HTTP semantic conventions). Health and readiness checks are not traced; 5xx responses, including recovered panics, mark the span as an error. |
| C58 | Every incoming request is treated as a public endpoint (`otelhttp.WithPublicEndpointFn`): a client's `traceparent` becomes a span link, never the parent. The API always starts its own trace and applies its own sampling, so clients cannot choose trace IDs or hide their requests from tracing (the counterpart of C33 for request IDs). When trusted internal callers exist (for example background workers under D09), the same hook can mark them as trusted. |
| C59 | Request IDs and trace IDs coexist with distinct roles: `request_id` (C33) is the always-present support handle (response header, problem `instance`, every request log line), available without any tracing setup; when a request is traced and sampled, its log records also carry `trace_id` and `span_id` (the fields log tools link on), and its server span carries a `request.id` attribute, so either ID leads to the other. The trace ID does not replace the request ID, because with tracing off (C55) there is no trace ID. |
| C60 | Trace IDs are added to logs by a small handler of our own (`observability.traceHandler`) that only reads the current span. `remychantenay/slog-otel` was not used: by default it copies every log record and its attributes into the trace as span events before redaction runs (so secrets could reach the trace backend), adds client-controlled baggage to logs, and marks spans as errors on ERROR logs; safety would depend on options staying set and defaults never changing. Documented gap: the library's useful part is about ten lines. |
| C61 | Traces record the shape of database and cache work, never its data. PostgreSQL spans come from `exaring/otelpgx` (v0.12.0): SQL text with placeholders (`db.query.text`), operation as span name, connection details without password, and connection-acquire waits; parameter values are never recorded (`WithIncludeQueryParameters` is not used), which relies on queries always being parameterized. Redis spans come from `redisotel` (v9.22.0) with `WithDBStatement(false)`: span names are command names (`get`, `set`); command arguments, which carry cached values and keys, are not recorded; `db.connection_string` holds only `redis://host:port`. Instrumentation is attached in `bootstrap` only when tracing is on, so the `postgres` and `redis` packages do not import OpenTelemetry and there is no overhead when off. |
| C62 | Trace export failures never affect requests: the SDK's batch processor exports in the background and holds at most 2,048 unsent spans, dropping newer ones when full (measured: 266 requests during a 70-second collector outage, slowest 61 ms). OpenTelemetry errors are throttled in our error handler: the first is logged at WARN at once, then at most one WARN per minute with a `suppressed` count (measured: 2 lines instead of 14 per 70 seconds, about 60 instead of 720 an hour). OpenTelemetry has no built-in throttle (documented gap); a general log-sampling library was not used because it would affect every log line. |
| C63 | Development traces are viewed in Jaeger (`jaegertracing/jaeger:2.21.0`), a regular Compose service with its UI at `http://jaeger.bool.test` and traces held in memory. In Compose the API exports to it by default (`OTEL_TRACES_EXPORTER=otlp`, `OTEL_EXPORTER_OTLP_ENDPOINT=http://jaeger:4318`); `OTEL_TRACES_EXPORTER=none` in `.env` turns it off. The application default outside Compose is unchanged (export off, C55). Chosen over `grafana/otel-lgtm`, whose Loki, Prometheus, and Grafana would stay empty until D07 decides log and metric shipping. Jaeger v2 serves its query API under `/api/v3`. **Superseded by C82.** |
| C64 | Business endpoints are versioned in the path, `/api/v1/...`; health and readiness stay unversioned (`/api/healthz`, `/api/readyz`). Chosen over header versioning (invisible in logs and traces), no versioning (fragile with self-hosted installs on different releases, C09), and date-based versions (needs a translation layer). See [API conventions](../platform/api-conventions.md). |
| C65 | JSON request and response fields use camelCase, matching the React/TypeScript frontend without a conversion layer. RFC 9457 fields, log attributes, OpenTelemetry attributes, and database columns keep their own conventions. |
| C66 | Paths use plural kebab-case resources with at most one level of nesting for real ownership; the tenant never appears in the path. Business actions use `POST /api/v1/{resources}/{id}/{action}` (for example `.../terminate`), each its own endpoint, permission, and audit record, instead of Google-style `:action` (awkward with chi and proxies) or status fields hidden in `PATCH`. |
| C67 | Resource IDs are UUIDv7, generated by PostgreSQL 18's native `uuidv7()`, stored as `uuid`, and serialized as strings. Chosen over sequential integers (enumerable, reveal counts), prefixed IDs (custom format), and ULID (no native PostgreSQL type). |
| C68 | Lists use page and size with a total (`?page=&pageSize=` returning `items`, `page`, `pageSize`, `total`), with a per-endpoint maximum page size; cursor pagination is a documented exception for unbounded lists such as the audit log. |
| C69 | Lists filter with named query parameters (ranges as `…From`/`…To`, free text as `q`) and sort with `sort=-field,field`; every filter and sort field is allow-listed per endpoint, and unknown ones are a 400 problem response. Chosen over JSON:API bracket syntax and query languages such as OData or RSQL (large security surface against authorization and tenant isolation). |
| C70 | The API contract is written first in OpenAPI 3.1 and `oapi-codegen` (v2.8) generates Go types and a typed chi server interface, so code that does not match the contract does not compile; the frontend will generate its TypeScript client from the same file. Chosen over `huma` (would replace the handler model and overlap C27, C37, C57), `swaggo/swag` (comment-driven, drifts; v2 still a release candidate), and hand-written specs. Set up with the first endpoint that needs it. **Superseded by C74.** |
| C71 | Validation problems carry an `errors` array, following RFC 9457's own example: each entry has `detail` and a JSON Pointer `pointer` (RFC 6901) for body fields, extended with `parameter` for query parameters (which a pointer cannot address) and `code`, a stable rule name clients can map to their own messages. Exactly one of `pointer` and `parameter` is set. Every failing field is reported at once, and submitted values are never included. |
| C72 | Our own problem types use absolute URIs `https://bool.mv/problems/<name>`, starting with `validation-error`: stable on every install (SaaS and self-hosted) because they name the product, not the server. Plain HTTP errors keep `about:blank`. Chosen over `tag:` URIs (never dereferenceable) and relative paths (resolve differently per host, breaking clients that switch on `type`). |
| C73 | Status codes for input: 400 (`about:blank`) only when the body cannot be parsed (empty, malformed, more than one JSON value); 413 when too large; 415 when not `application/json`; 422 `validation-error` for every field-level problem once parsed: wrong types, unknown fields, failed rules, and invalid query parameters. |
| C74 | Simple approach for now: request structs are written in Go with `go-playground/validator` tags (confirming C27 for request bodies), decoded by `httpinput.Decode` (size limit, one JSON value, unknown fields rejected), and no OpenAPI contract is maintained yet. Replaces C70: contract-first tooling was judged too heavy while the only client is the team's own, not-yet-integrated frontend and no third-party API is planned soon. When frontend integration starts, decide how to produce frontend types and Zod schemas from the Go structs (for example `hypersequent/zen` for Zod directly from validator tags, or OpenAPI with `orval`). Rules needing data (uniqueness, existence) belong to the application layer and database constraints, reporting through `problem.ValidationError` in the same 422 format. Known limits of Go's `encoding/json`: wrong-type and unknown-field errors stop decoding (reported alone), unknown fields and invalid dates carry no path (pointer `#`). |
| C75 | Go code is linted in CI with `golangci-lint` v2.14.0 (pinned image), configured in `apps/api/.golangci.yml`: the standard set (errcheck, govet, ineffassign, staticcheck, unused) plus gosec, errorlint, bodyclose, noctx, misspell, sqlclosecheck, and rowserrcheck. The `std-error-handling` preset ignores idiomatic unchecked `Close`/`Flush` errors; gosec and noctx do not run on tests (test servers and fake credentials are intended). contextcheck is off because it flags the deliberate `context.Background()` used for shutdown and flushing. The lint step runs first in CI and fails on any finding. |

## Current state

The [roadmap](../roadmap.md) holds the implementation status. In short: the API's
foundations (configuration, logging, HTTP, PostgreSQL, Redis, tracing, metrics) and
identity (Kratos, Hydra, the BFFs, users, disabled accounts) are implemented; `users`
and `countries` are the confirmed tables (C94, C121); tenancy, authorization, and audit
are designed (C115-C120) and next, each table's fields to be confirmed before it is
created (C121).

## Interpretation

Removing identity/authorization services from Compose does not select replacement
engines or authorize bypassing their protections. PostgreSQL-only does not
automatically remove application ports. Redis caching does not make Redis the
authority for business records or audit history.

Detailed documents describe requirements and proposals; only a recorded user
decision changes a row from open to confirmed. Earlier archived approvals do not
carry forward automatically.

See [ADR 0001](../adr/0001-api-baseline.md), [ADR 0002](../adr/0002-tool-and-provider-selection.md), and [product scope](../product/scope.md).
